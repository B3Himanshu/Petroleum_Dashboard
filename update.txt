--------------------------------------------------------------------------------
1. WHAT “LIGHT MODE” MEANS IN THIS APP
--------------------------------------------------------------------------------
- The document root <html> gets a class: either "light" or "dark"
  (see ThemeContext: document.documentElement.classList.add(theme)).
- Tailwind is configured with darkMode: ["class"], so utilities like
  "dark:bg-..." only apply when <html class="dark">.
- Default semantic colors for LIGHT mode live in CSS :root { ... } as HSL
  triples (no "hsl()" wrapper). Components use them via hsl(var(--token)).

- When dark mode is DISABLED by env, the app stays in light mode only: the
  header theme toggle is hidden and theme is forced to "light".

2. ENVIRONMENT — HOW LIGHT-ONLY / TOGGLE IS APPLIED
--------------------------------------------------------------------------------

2a) Runtime (authoritative for toggle visibility)
    File: backend/server.js — GET /api/ui-config
    Response JSON: { "darkModeToggle": true | false }

    Env var read on server: DARK_MODE_TOGGLE
    - If unset or any value except case-insensitive "false" → darkModeToggle true
    - If "false" → darkModeToggle false (no dark switch; user stays in light)

    Example (backend/.env.example):
      # DARK_MODE_TOGGLE=false

2b) Build-time default (Vite client bundle)
    File: frontend/vite.config.mjs
    - Reads backend/.env key DARK_MODE_TOGGLE via readBackendEnvValue()
    - Falls back to frontend env VITE_DARK_MODE_TOGGLE, then defaults to enabled
    - Defines: import.meta.env.VITE_DARK_MODE_TOGGLE as string "true" or "false"

    This bakes an initial default before /api/ui-config runs (useful for Docker
    builds where backend .env may be missing at build time).

2c) Client logic
    File: frontend/src/contexts/ThemeContext.jsx

    parseBuildDarkModeToggle():
    - Reads import.meta.env.VITE_DARK_MODE_TOGGLE
    - Empty/undefined → treat as true (toggle enabled)
    - "false" or "0" → toggle disabled

    Initial theme state:
    - If toggle disabled → theme starts as 'light'
    - If toggle enabled → localStorage 'theme' or default 'dark'

    After fetch('/api/ui-config'):
    - If response.darkModeToggle === false → sets darkModeToggleEnabled false
    - Effect: if !darkModeToggleEnabled, theme forced to 'light'

    uiConfigHydrated: header waits before showing toggle (see Header.jsx) so
    build-time "true" does not flash a toggle when server says false.

2d) ThemeProvider mount
    File: frontend/src/App.jsx — wraps routes with <ThemeProvider>.

6. TAILWIND — MAPPING TO CSS VARIABLES (LIGHT WHEN html.light OR NO .dark)
--------------------------------------------------------------------------------
File: frontend/tailwind.config.mjs

- darkMode: ["class"] — dark utilities require class "dark" on ancestor (html)
- extend.colors maps border, background, foreground, primary, secondary,
  destructive, muted, accent, popover, card, sidebar.*, chart.*, metric.*
  → hsl(var(--token))

- borderRadius lg/md/sm → var(--radius) family
- boxShadow: card, soft, glow (glow uses hsl(var(--primary) / 0.3))
- fontFamily sans → Plus Jakarta Sans

In JSX, prefer semantic classes: bg-background, text-foreground, bg-card,
border-border, text-muted-foreground, hsl(var(--chart-blue)) in charts.

Many components pair light base + dark: variant, e.g. bg-blue-50 dark:bg-blue-950/20
— in light mode only the first part applies.

8. RESPONSIVE BREAKPOINTS (TAILWIND) — SHARED BY LIGHT & DARK
--------------------------------------------------------------------------------
Standard Tailwind defaults (used across the app):
  sm:  640px   — phone → small tablet; many layouts switch to row / larger type
  md:  768px   — tablet
  lg:  1024px  — desktop: sidebar + content margin, wider grids, open sidebar
  xl:  1280px
  2xl: 1400px  — container max width in tailwind.config.mjs

Rule file: .cursor/rules/responsive-design.mdc
- Mobile-first base styles; enhance with sm:/md:/lg:
- When fixing bugs, preserve desktop (sm+) unless explicitly changing it
